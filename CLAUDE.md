# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Kararsızım** — a polling/voting web app prototype (Turkish). Members create polls with 2–5 options; anyone (member or guest) can vote once per poll. The full spec, data model, API contract, UI guidelines, and phased roadmap live in [docs/kararsizim-proje-plani.md](docs/kararsizim-proje-plani.md) — read it before making product decisions; this file only covers what's needed to work in the code.

The project is being built phase-by-phase (see "Yol Haritası" in the spec doc) at the user's direction — don't jump ahead to a later phase's scope without being asked. Faz 1 (backend skeleton, models, auth) and Faz 2 (poll create/list/detail/vote + a minimal functional frontend) are done. `vercel.json` and full Faz 3 styling (Bölüm 10 — vivid accent colors, micro-interactions) don't exist yet; `public/` currently has bare-bones CSS on purpose.

A live Supabase project (`kararsizim`, ref `lrqexjgxdfackfwvazls`, eu-central-1) backs local dev — `DATABASE_URL` in `.env` points at its transaction-mode pooler. The Supabase MCP connector is available in-session for inspecting/migrating that project directly (`list_tables`, `execute_sql`, `apply_migration`, etc.) without needing the raw connection string each time.

## Commands

All commands run from the repo root with the venv at `.venv` (Windows).

```bash
# install/sync dependencies
./.venv/Scripts/python.exe -m pip install -r requirements.txt

# run the API locally with reload
./.venv/Scripts/python.exe -m uvicorn api.main:app --reload

# apply migrations (reads DATABASE_URL from .env via api/config.py)
./.venv/Scripts/python.exe -m alembic upgrade head

# create a new migration (hand-write it — see Migrations note below)
./.venv/Scripts/python.exe -m alembic revision -m "message"
```

There is no test suite, lint config, or frontend build step yet.

## Architecture

- **Sync SQLAlchemy/SQLModel, not async**, even though FastAPI endpoints are `def`/`async def` mixed — this is deliberate for serverless (Vercel): each request gets its own short-lived `Session`, and `engine` in [api/database.py](api/database.py) uses `NullPool` because Supabase's pgbouncer (transaction-mode pooling) does the real pooling. Don't introduce a process-wide connection pool or async engine without revisiting this.
- **Config** ([api/config.py](api/config.py)): `pydantic-settings` reads `.env` (`DATABASE_URL`, `JWT_SECRET`, `JWT_EXPIRE_MINUTES`, `ENVIRONMENT`). `.env` is gitignored; `.env.example` documents the shape. `get_settings()` is `lru_cache`d — call it, don't re-instantiate `Settings()`.
- **Auth** ([api/auth.py](api/auth.py), [api/deps.py](api/deps.py), [api/routers/auth.py](api/routers/auth.py)): passlib/bcrypt for password hashing, PyJWT for tokens. On register/login the server sets the JWT in an **httpOnly cookie** (`access_token`) — there is no bearer-token flow and no server-side session store. `get_current_user` (dependency) requires a valid cookie and 401s otherwise; `get_current_user_optional` returns `None` instead, used for endpoints reachable by both members and guests (e.g. voting). `POST /api/auth/register` auto-logs the user in (sets the cookie) rather than requiring a separate login call.
- **Models** ([api/models.py](api/models.py)): `User`, `Poll`, `PollOption`, `Vote` per the spec doc's data model section. Guest votes are tracked by a `guest_id` UUID (cookie-based, no account) instead of `user_id`. The one-vote-per-poll rule is enforced by **partial unique indexes** on `vote(poll_id, user_id) WHERE user_id IS NOT NULL` and `vote(poll_id, guest_id) WHERE guest_id IS NOT NULL` — these can't be expressed in SQLModel's column-level `unique=True`, so they're hand-written directly in the Alembic migration, not autogenerated.
- **Migrations**: [alembic/env.py](alembic/env.py) is customized to pull `DATABASE_URL` from `api.config.get_settings()` instead of `alembic.ini` (the `sqlalchemy.url` placeholder there is unused) and points `target_metadata` at `SQLModel.metadata` via `api.models`. Because of the partial-index requirement above, prefer hand-writing migrations over `alembic revision --autogenerate` for anything touching `vote`.
- **Routing**: routers live under `api/routers/` and are included in [api/main.py](api/main.py) with their own `/api/...` prefix already set on the `APIRouter` (not added at include time).
- **Guest voting** ([api/routers/polls.py](api/routers/polls.py)): guests (no `access_token` cookie) vote using a `guest_id` UUID cookie, minted lazily on first vote (not on page view) and read back to enforce one-vote-per-poll and to report `voted_option_id`. A `sqlalchemy.exc.IntegrityError` on insert (the partial-unique-index race) is caught and turned into a 409 — the app-level pre-check is a fast path, the DB constraint is the real guarantee.
- **Poll serialization**: `_serialize_poll()` in `polls.py` is the single place that computes vote counts/percentages and the viewer's `voted_option_id`; reuse it rather than duplicating that logic (list endpoint intentionally uses a lighter `PollListItem` without per-option breakdown).
- **Frontend** (`public/`): static HTML + vanilla JS, no build step, no framework. [api/main.py](api/main.py) mounts `StaticFiles(directory="public", html=True)` at `/` (after the API routers, so `/api/*` still matches first) so the same-origin `fetch()` calls in `public/js/*.js` work in local dev without CORS. `js/api.js` is the one fetch wrapper (throws on non-2xx, extracts FastAPI/Pydantic error `detail`); `js/auth.js`'s `initNav()` runs on every page to paint the header's login state and is the auth check other pages (`requireLogin()`) build on.
- **Deployment target**: Vercel, with the FastAPI app intended to serve `/api/*` as a serverless function and a static `public/` directory for the frontend (no SPA framework — plain HTML/CSS/JS calling the API via `fetch()`). This shapes some of the choices above (sync engine + NullPool, cookie-based auth instead of server sessions) even before deployment config exists.
